# Incident RCA — NM1020 monitoring outage (2026-08-13)

**Status:** Resolved · **Severity:** Single-asset monitoring gap (no patient-safety or magnet impact)
**Asset:** NM1020 — North Mississippi Medical Center, West Point
**Author:** Prepared with Claude Code · **Date:** 2026-08-13

---

## Summary

For **1 hour 37 minutes**, the NM1020 dashboard showed the unit **offline**. The magnet itself
was never at risk and the on-site MagMon controller never stopped working. The Raspberry Pi
gateway that reports NM1020's readings to the cloud **lost local DNS resolution** and therefore
could not resolve the Supabase hostname to send telemetry. Every path that uses a raw IP address —
SSH, Tailscale, and the MagMon device query — kept working, which is why the unit *looked* healthy
everywhere except the dashboard. Restoring a working DNS resolver on the Pi and restarting the
gateway brought it straight back online.

## Root cause (confirmed)

**Local DNS resolution failure on the NM1020 Raspberry Pi.** The gateway process was running and
successfully reading the MagMon, but could not resolve `wxygirzfxutvtfkxxcvw.supabase.co`, so its
`report_telemetry` HTTPS calls failed before a connection was ever made.

Two independent lines of evidence confirm this:

1. **Gateway journal** — every failure in the outage window is the same name-resolution error:
   ```
   requests.exceptions.ConnectionError:
   HTTPSConnectionPool(host='wxygirzfxutvtfkxxcvw.supabase.co', port=443):
   Max retries exceeded ... [Errno -3] Temporary failure in name resolution
   ```
   `Errno -3` (`EAI_AGAIN`) means the resolver could not be reached or returned no answer — a DNS
   problem, not a Supabase or connectivity problem.

2. **Blast radius (backend query)** — NM1020 was the **only** unit with zero readings in the
   window. The other 12 actively-reporting units each logged ~19 readings across the same window,
   and Supabase served all of them normally. A cloud-side or backbone outage would have hit the
   whole fleet; it hit exactly one Pi.

## Why the dashboard "offline" was misleading (contributing factors)

These didn't cause the outage, but they made it look like a device fault and slowed diagnosis:

1. **"Offline" is inferred purely from telemetry staleness.** The dashboard flags a unit offline
   when `last_seen_at` ages past its threshold. It has no way to distinguish *"the magnet is
   faulted"* from *"the device is unreachable"* from *"the Pi can't reach the cloud."* All three
   render identically.
2. **Raw-IP paths masked the fault.** SSH, Tailscale node status (showed **online**), and the
   MagMon query (`http://172.31.62.17` — a raw IP) all worked, because none of them need DNS. Only
   the single DNS-dependent call — the Supabase hostname — failed. The Pi looked completely healthy.
3. **The MagMon clock reads 2006.** These controllers have no working real-time clock, so their
   timestamps are meaningless (`13-May-06`). This created a plausible but false "the device
   rebooted" lead early in the investigation.
4. **Gateway logs were buffered.** The script currently deployed on this Pi runs under a systemd
   unit **missing `PYTHONUNBUFFERED=1`**, so Python block-buffered its stdout. Live `journalctl -f`
   showed nothing between error bursts, making a running process look "frozen" and hiding the DNS
   traceback until a buffer flush.

## Underlying trigger of the DNS failure (to confirm)

**Proven:** DNS resolution on the Pi stopped working.
**Most likely trigger (not yet confirmed):** the resolver the Pi was configured to use stopped
answering. Recovery came from pointing `/etc/resolv.conf` at a public resolver — which indicates the
*previously configured* nameserver (most commonly the on-site iR305 router's DNS forwarder, or a
resolver handed out via DHCP) became unreachable, or `resolv.conf` was rewritten/cleared by a DHCP
lease renewal while LAN routing kept working.

> **One detail to close this out:** what was in `/etc/resolv.conf` before the fix, and exactly what
> was changed to recover? That confirms whether this was a wiped resolver, a dead router DNS
> forwarder, or a lease-renewal overwrite — and dictates the precise durable fix below.

## Corrective and preventive actions

| # | Action | Type | Status |
|---|---|---|---|
| 1 | Repoint Pi resolver to a public DNS server + restart gateway | Immediate | ✅ Done — recovered 18:35 UTC |
| 2 | Make DNS durable on the Pi so a lease renewal / router blip can't wipe it — pin `static domain_name_servers=1.1.1.1 8.8.8.8` in `dhcpcd.conf` (or the systemd-resolved equivalent) and verify it survives a reboot | Preventive | ☐ Recommended |
| 3 | Redeploy NM1020 with the current gateway script + systemd unit that sets `PYTHONUNBUFFERED=1` — gives live logs, the minute-resolution batch reporter, and the device-clock re-anchor fix | Preventive | ☐ Recommended |

Both email/push. This names the NM1020 fault on the first alert instead of after an hour of investigation | Detection | ✅ Done — shipped 2026-08-13 (migration `alerts_disambiguate_reporting_stalled`) |
| 5 | Optional gateway resilience: on repeated name-resolution failures, fall back to a known-good resolver for the Supabase host | Hardening | ☐ Optional |

## Data loss

The ~97-minute gap in NM1020's stored history **cannot be backfilled**. The script currently on this
Pi reports only the single latest reading, and even the newer batch reporter only pulls the last ~60
minutes from the device on recovery — neither can reconstruct a 97-minute gap after the fact. The gap
is cosmetic for trend charts and carries no operational consequence; it is noted here for
completeness.

## Key evidence (appendix)

- **Gateway journal:** `socket.gaierror: [Errno -3] Temporary failure in name resolution` for
  `wxygirzfxutvtfkxxcvw.supabase.co`, repeating every cycle through the outage window.
- **Backend query (blast radius):** NM1020 = 0 readings in 16:59–18:35 UTC; 12 other live units = ~19
  readings each over the same window; NM1020 first post-recovery reading at 18:35:51 UTC.
- **On-site checks:** `curl http://172.31.62.17/...` returned healthy MagMon data throughout;
  Tailscale reported the node online; SSH into the Pi worked — all raw-IP paths, none DNS-dependent.
